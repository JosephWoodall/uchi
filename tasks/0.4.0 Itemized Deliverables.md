# Uchi v0.4.0 — Itemized Deliverables

## What to expect, broadly

v0.3.0 gave Uchi a trained proposer (FLUX) behind a verifier that grounds or
abstains. v0.4.0 is about **autonomy**: turning that pairing into an agent that
can be handed a goal and go get it done — reading/writing its own files, running
code, browsing the web, and delegating pieces of the problem to specialized
sub-instances of itself — with a human able to check in on (and pause/resume)
what it's doing at any point. Concretely, by the end of 0.4.0 there will be two
public classes: a **single-instance `Uchi`** (moved to `uchi.Core`, unchanged
internals — a lightweight node in a larger network) and a new **`MetaUchi`
orchestrator** (the default facade) that wraps one or more single-instance
nodes with tool calling, a Python scratchpad, web navigation, and task
delegation, while keeping the exact same string-in/string-out contract so
everything still compounds. FLUX itself also grows — a larger model is the
other half of "smarter, more autonomous."

The overarching goal for v0.4.0 is to transform Uchi from a passive,
deterministic memory engine into an autonomous cognitive operating system that
orchestrates its own specialized instances and wields external tools to
independently solve complex, multi-step goals.

## Revision note (post-audit)

This list was audited against the actual codebase, not just designed on paper.
Findings that reshaped the ordering below:

- **`OmniRouter` does not exist.** `uchi/simple.py:93` documents `u.router`
  as "the underlying OmniRouter," but no `self.router` is ever assigned — the
  real object is `self.pipeline`, a `GenerateAndGround` instance. Any item
  that targets "the OmniRouter" actually targets `GenerateAndGround`. Fix the
  dead docstring reference as a drive-by while touching this file.
- **Three items already have working prototypes** that were about to be
  rebuilt from scratch: `uchi/code_engine.py`'s `REPLOracle` already does
  subprocess/tempfile-based execution (currently compile-check only, not full
  run-and-capture — extend it, don't replace it). `uchi/swarm.py`'s
  `SwarmSynthesizer` already decomposes a question into sub-questions, runs
  them in parallel via `ThreadPoolExecutor`, and aggregates — in-process,
  zero serialization. `uchi/intent_router.py` already does cheap
  regex/heuristic classification ahead of expensive paths.
- **Item 0 (FLUX scale-up) is a parallel track, not a blocking first step.**
  Nothing below structurally depends on a bigger FLUX to be *built* — only to
  be *validated against* at exit criteria. It's GPU-bound training time; run
  it alongside everything else, not before it.
- **The facade swap (formerly Item 15) moved to Item 1.** It's a mechanical
  rename/wrap and doesn't need the IQ router finished first. Shipping a
  stubbed `MetaUchi` early means every other item builds against the final
  public API instead of internal scaffolding that gets re-plumbed later.
- **Cut:** a dedicated Token Stream Communication Protocol (formerly Item 8)
  and the Background Dreaming Daemon (formerly Item 17). See "Deferred to
  v0.5" at the bottom for why.

Items are ordered by real (verified) dependency. Do not start an item until
the items it depends on are complete — except Item 0, which runs continuously
in parallel with everything else.

## 0. Scale Up FLUX *(parallel track — not a blocking dependency)*

**Problem:** v0.3.0's FLUX is ~116M parameters, trained on a light token budget
(well under Chinchilla-optimal). That ceiling caps how good a proposer
Meta-Uchi's autonomous loop has to work with — bigger, more capable reasoning
requires more capacity, not just better orchestration around a small model.

**Intent:** Increase FLUX's parameter count and training token budget for
0.4.0 (exact target TBD against available compute/GPU budget). Carry forward
the two structural wins identified as the biggest levers coming out of v0.3.0:
cut the vocab (currently a 100K-token embedding table eats the majority of
model params — reclaiming that capacity for reasoning layers) and fuse the SSM
scan (removes the throughput ceiling that currently caps tokens-per-hour of
training, so a bigger model can actually see enough data). A bigger, better
FLUX is what Meta-Uchi's tool-calling/reasoning loop is actually delegating to.
This is a compute-bound background job — kick it off now and let it run
alongside Items 1–13; only the exit-criteria validation at the end needs it
finished.

## 1. Meta-Uchi Default Facade (stub)
**Problem:** If every other item builds against internal scaffolding (`GenerateAndGround`, `swarm.py`, `intent_router.py` called directly), it all has to be re-plumbed later when the public API changes. Doing the facade swap last (as originally planned) guarantees rework.
**Intent:** Refactor the public API now, early, before the interesting logic exists: `from uchi import Uchi` instantiates a new `MetaUchi` class; the existing single-instance engine moves to `uchi.Core` for users who want raw trie access. At this stage `MetaUchi` can be a thin wrapper that routes every call straight to a single `Core` instance — no real tool calling, no real delegation yet. Every later item (2–13) attaches its capability to this stable facade instead of to internal classes. Also fix the dead `u.router` docstring reference at `uchi/simple.py:93` while touching this file — replace it with the real name (`pipeline` / `GenerateAndGround`).

## 2. Filesystem Path Guard
**Problem:** Giving an autonomous system the ability to write and execute files is dangerous. But `uchi/code_engine.py` already proves the actual risk surface is small: it writes to `tempfile.NamedTemporaryFile` and runs `subprocess.run([sys.executable, ...])` today, safely, without a dedicated sandbox subsystem. Building a full chrooted workspace subsystem is solving a bigger problem than the one that exists.
**Intent:** Add a single path-validation helper (`uchi/workspace.py`, ~30 lines): resolve every file path tool calls touch against a fixed root (`uchi/workspace/`), refuse anything that escapes it via `os.path.realpath` + prefix check, and reuse the existing tempfile/subprocess pattern from `code_engine.py` for execution. This is a guard rail, not a subsystem.

---

## 3. Python Scratchpad Environment
**Problem:** Uchi natively predicts discrete tokens; it cannot natively calculate continuous regressions, calibrate probabilistic uncertainties, or dynamically test code.
**Intent:** Extend `uchi/code_engine.py`'s `REPLOracle` (currently `ast.parse` + `py_compile` only — verifies syntax but never runs the code) into a full execution path: run the code via the same subprocess pattern already in place, and return `stdout`, `stderr`, and return code as text tokens. Do not write a second, parallel oracle — `uchi/procedural_memory.py` already has its own separate `REPLOracle` class with the same name; consolidate to one canonical implementation while doing this work rather than introducing a third.
**Depends on:** 2

---

## 4. Tool Calling Interface
**Problem:** Uchi currently has slash commands, but no generalized mechanism to autonomously decide to take an action, execute it, and ingest the result. This is the real gating item — Items 5, 6, 7, 9, 10, 11, 12, 13 all sit downstream of it.
**Intent:** Implement a formalized tool-calling grammar in the trie. Uchi needs to be able to output a specific token sequence (e.g., `<|tool_call|> write_file(path, content) <|end_tool|>`) that halts generation, triggers a local Python function execution, and appends the result to the context before resuming. Initial tools must include filesystem operations and access to the Python Scratchpad. Ship this with logging from day one (see Item 9 below on observability) instead of retrofitting traces later.
**Depends on:** 3

---

## 5. Goal State Compression & Memory Compaction
**Problem:** Tool calling, web browsing, and code execution generate massive amounts of token noise (raw HTML, long stack traces, large tool outputs). Uchi's trie architecture will lose long-context coherence and goal focus if the active context window fills up with raw execution logs.
**Intent:** Introduce a "Memory Compaction" mechanism in `GenerateAndGround` (the actual pipeline object — see revision note above) and the `MetaUchi` state tracker. Before the context window exceeds a designated token threshold, trigger a deterministic summarization pass: read recent tool outputs, update a persistent `GoalState` object with what was learned or accomplished, and drop the raw tool logs from active memory. **North Star constraint:** the summarization pass must itself be oracle-gated — it may only write claims into `GoalState` that trace back to an actual tool output, never a free-form paraphrase. An ungrounded summarizer is a confabulation backdoor into the trie.
**Depends on:** 4

---

## 6. Self-Healing Loop Prevention
**Problem:** The most common failure mode for autonomous agents writing code is getting stuck in an infinite loop: write bad code -> get error -> write the exact same bad code -> get error.
**Intent:** Implement a strict "Negative Pathway Penalty" in the MCTS inner monologue. If a tool call (like the Scratchpad) returns an error, the trie explicitly penalizes the exact sequence of tokens that generated that call. This forces the search engine to explore a structurally different path on the next attempt, mathematically guaranteeing it won't loop on the same failure.
**Depends on:** 4

---

## 7. Concurrent / Async Tool Execution
**Problem:** If Meta-Uchi needs to read 5 webpages or run 3 independent Python scripts, executing them sequentially creates an enormous bottleneck that destroys the Operations Per Second metric. Note: `uchi/swarm.py` already demonstrates the concurrency primitive (`ThreadPoolExecutor`) for parallel sub-question solving — this item is the same pattern applied at the tool-call level.
**Intent:** Introduce a `<|tool_call_async|>` grammar element. This allows Meta-Uchi to fire off multiple external tool requests simultaneously without halting its internal monologue. It continues reasoning and ingests the results asynchronously as they stream back into the context.
**Depends on:** 4

---

## 8. Dynamic Tool Registration (Zero-Shot Tool Learning)
**Problem:** Hardcoding tools limits what Uchi can do. Integrating proprietary databases or external APIs currently requires modifying Uchi's source code. Note: `uchi/skill_registry.py` already has a working register/discover/dispatch pattern (markdown-frontmatter driven) — reuse its structure rather than inventing a second registry mechanism.
**Intent:** Allow Meta-Uchi to ingest Python docstrings and function signatures natively as "knowledge." A user can pass a Python file to `u.learn_tools("database_client.py")`, and Meta-Uchi will parse the functions, add them to its active tool registry (extending `SkillRegistry`, not replacing it), and understand how to call them dynamically without hardcoded integrations.
**Depends on:** 4

---

## 9. Intelligence Quotient (IQ) Task Router
**Problem:** Not all tasks require the full reasoning capacity of the entire Uchi network. `uchi/swarm.py`'s `SwarmSynthesizer.answer()` already decomposes and aggregates, but it does so unconditionally — it always calls `_decompose()` (a FLUX proposer round-trip) before checking whether the question was even complex enough to need it.
**Intent:** This is a cheap heuristic pre-check, not new infrastructure. Reuse the pattern already proven in `uchi/intent_router.py` (regex/length/keyword classification) to gate `SwarmSynthesizer._decompose()`: low-score tasks skip straight to a single `Core` pass; only high-score tasks pay for decomposition and parallel dispatch. No new communication protocol between nodes is needed — `swarm.py`'s in-process `ThreadPoolExecutor` dispatch already works and has no demonstrated latency problem to justify one.
**Depends on:** 4

---

## 10. Human-in-the-Loop (HitL) Yielding
**Problem:** Autonomous agents inevitably get stuck or encounter high-risk actions. If they brute-force their way through ambiguity, they break things.
**Intent:** Introduce a `<|yield_to_user|>` tool call. If the IQ Task Router detects extreme uncertainty, or if a tool fails repeatedly, Meta-Uchi pauses its token stream, asks the user for clarification (e.g., "I cannot find the login button, should I proceed?"), and seamlessly ingests the human's response to continue the task.
**Depends on:** 4, 9

---

## 11. Web Navigation Toolkit
**Problem:** To have human-like capabilities, Uchi needs to navigate the web. Feeding raw HTML into the trie will destroy the token space and cause massive hallucination. Note: `uchi/web_search.py` already retrieves structured, parsed content (DuckDuckGo, Wikipedia, arXiv, News RSS) with zero browser dependency — this already covers most "look something up" goals.
**Intent:** Scope this down from the original "headless Chromium + full accessibility tree" plan. First, expose `MultiSourceSearch` as a tool call through Item 4 — this alone closes most of the gap. Only add real browser automation (Playwright/Chromium, DOM parsed into abstracted UI tokens like `[LINK: "Log In"]`) as a follow-up if a concrete goal requires interactive navigation (clicking, form-filling) that static retrieval can't satisfy. Don't pay for a browser dependency until a real task needs one.
**Depends on:** 4, 5

---

## 12. Agentic State Checkpointing (Pause and Resume)
**Problem:** If Meta-Uchi is 100 steps into a complex task and the process stops, all active reasoning, `GoalState` tracking, and task progress are lost.
**Intent:** Because Uchi is deterministic, the active `MetaUchi` state can be fully serialized. Implement checkpointing to save the `GoalState`, tool logs, and active token streams to disk. This allows a user to hit `Ctrl+C` to pause the agent, and run `u.resume("task_state.uchi")` later to pick up exactly where it left off.
**Depends on:** 4, 5

---

## 13. Episodic Memory & "Macro" Skill Distillation
**Problem:** When Meta-Uchi successfully solves a difficult, multi-step problem, it stores the solution in transient memory. The next time it faces the same goal, it wastes operations reasoning through the exact same steps from scratch. Note: `uchi/episodic_memory.py` already exists as a starting point — check its current scope before building a second episodic store.
**Intent:** Implement a background "Distillation" pass upon task success. Meta-Uchi extracts the successful sequence of tool calls, removes errors and dead-ends, and compiles it into a reusable "Macro". This sequence is permanently ingested into the core trie, so the next time it encounters a similar goal, it deterministically recalls the fast-path macro instead of reasoning step-by-step.
**Depends on:** 4, 5

---

## 14. Agentic Observability (The "Glass Brain" UI)
**Problem:** When a single-instance sequence predictor fails, you can debug the prompt. When an autonomous orchestrator fails after delegating to several nodes, making concurrent tool calls, and reading web pages, debugging it without a trace is impossible.
**Intent:** Not a gated deliverable scheduled for the end — build a thin structured logger into Item 4's tool-calling interface from day one (which node, which tool, what arguments, what result, what error), and add the TUI visualizer as a display layer over that log once Items 4, 7, and 9 exist. Building the trace format after the fact means retrofitting instrumentation into five already-built subsystems instead of getting it for free.
**Depends on:** 4 (logging from day one); 7, 9 (full visualizer)

---

## 15. Uchi Operations Per Second (OPS) Benchmark Harness
**Problem:** MMLU and SWE-bench measure static intelligence, but v0.4.0 is about autonomous agency. There is no existing metric to measure how fast and effectively Uchi can execute an autonomous loop.
**Intent:** Create a new benchmark harness: `benchmarks/ops_benchmark.py`. This measures **Uchi Operations Per Second (OPS)**. A single operation is defined as a complete inner-monologue cycle ending in a successful, syntactically valid tool call. This only needs Item 4 (a real tool call loop) and Item 1's stub facade to exist — it does not need the full IQ router or delegation logic finished first.
**Depends on:** 1, 4

---

## Deferred to v0.5 (cut from v0.4.0 scope)

- **Token Stream Communication Protocol** *(formerly Item 8)* — premised on
  JSON/IPC serialization overhead between `Meta-Uchi` and specialized nodes
  destroying latency. No out-of-process or networked node boundary exists
  anywhere else in this plan to justify it, and `uchi/swarm.py` already proves
  in-process `ThreadPoolExecutor` dispatch works with zero serialization cost.
  Revisit only if a real networked/distributed node requirement emerges.
- **Background Dreaming Daemon (Idle Self-Play)** *(formerly Item 17)* —
  stacks three unvalidated dependencies (Web Toolkit, Scratchpad, Episodic
  Distillation) with no defined reward/success signal beyond "the same
  grounding oracle." Revisit once Items 1–15 are proven in production use,
  not as a v0.4.0 exit requirement.

## Expected Benchmarks / Exit Criteria for v0.4.0

Before v0.4.0 can ship, it must be evaluated against the following criteria:

1. **FLUX Scale-Up Baseline:** the 0.4.0 FLUX model must be measurably larger
   (params) and trained on a materially larger token budget than v0.3.0's,
   with a documented before/after on generation coherence (not just loss).
2. **OPS Baseline:** `ops_benchmark.py` must establish a baseline execution speed for a 10-step autonomous task.
3. **Context Coherence:** `Meta-Uchi` must successfully execute a 25-step task without dropping the original user intent.
4. **Zero-Regression on v0.3.0:** MMLU no-parse rates and SWE-bench code generation rates must not regress from the v0.3.0 final numbers when run through the `Meta-Uchi` facade.
5. **Self-Healing Validation:** A test case designed to fail on the first attempt must prove that Uchi successfully alters its code path and resolves the error without looping.
6. **Web Navigation Baseline:** Establish a baseline score for autonomous web navigation capabilities (static retrieval via `MultiSourceSearch`; browser automation only if Item 11's follow-up scope was triggered).
