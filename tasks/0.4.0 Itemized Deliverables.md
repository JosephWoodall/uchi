# Uchi v0.4.0 — Itemized Deliverables

## What to expect, broadly

v0.3.0 gave Uchi a trained proposer (FLUX) behind a verifier that grounds or
abstains. v0.4.0 is about **autonomy**: turning that pairing into an agent that
can be handed a goal and go get it done — reading/writing its own files, running
code, browsing the web, and delegating pieces of the problem to specialized
sub-instances of itself — with a human able to check in on (and pause/resume)
what it's doing at any point. Concretely, by the end of 0.4.0 there will be two
public classes: a **single-instance `Uchi`** (moved to `uchi.Core`, unchanged
internals — a lightweight node in a larger network) and a new **`MetaUchi`
orchestrator** (the default facade) that wraps one or more single-instance
nodes with tool calling, a Python scratchpad, web navigation, and task
delegation, while keeping the exact same string-in/string-out contract so
everything still compounds. FLUX itself also grows — a larger model is the
other half of "smarter, more autonomous."

The overarching goal for v0.4.0 is to transform Uchi from a passive,
deterministic memory engine into an autonomous cognitive operating system that
orchestrates its own specialized instances and wields external tools to
independently solve complex, multi-step goals.

## Revision note (post-audit)

This list was audited against the actual codebase, not just designed on paper.
Findings that reshaped the ordering below:

- **`OmniRouter` does not exist.** `uchi/simple.py:93` documents `u.router`
  as "the underlying OmniRouter," but no `self.router` is ever assigned — the
  real object is `self.pipeline`, a `GenerateAndGround` instance. Any item
  that targets "the OmniRouter" actually targets `GenerateAndGround`. Fix the
  dead docstring reference as a drive-by while touching this file.
- **Three items already have working prototypes** that were about to be
  rebuilt from scratch: `uchi/code_engine.py`'s `REPLOracle` already does
  subprocess/tempfile-based execution (currently compile-check only, not full
  run-and-capture — extend it, don't replace it). `uchi/swarm.py`'s
  `SwarmSynthesizer` already decomposes a question into sub-questions, runs
  them in parallel via `ThreadPoolExecutor`, and aggregates — in-process,
  zero serialization. `uchi/intent_router.py` already does cheap
  regex/heuristic classification ahead of expensive paths.
- **Item 0 (FLUX scale-up) is a parallel track, not a blocking first step.**
  Nothing below structurally depends on a bigger FLUX to be *built* — only to
  be *validated against* at exit criteria. It's GPU-bound training time; run
  it alongside everything else, not before it.
- **The facade swap (formerly Item 15) moved to Item 1.** It's a mechanical
  rename/wrap and doesn't need the IQ router finished first. Shipping a
  stubbed `MetaUchi` early means every other item builds against the final
  public API instead of internal scaffolding that gets re-plumbed later.
- **Cut:** a dedicated Token Stream Communication Protocol (formerly Item 8)
  and the Background Dreaming Daemon (formerly Item 17). See "Deferred to
  v0.5" at the bottom for why.

Items are ordered by real (verified) dependency. Do not start an item until
the items it depends on are complete — except Item 0, which runs continuously
in parallel with everything else.

## 0. Scale Up FLUX *(parallel track — not a blocking dependency)*

**Problem:** v0.3.0's FLUX is ~116M parameters, trained on a light token budget
(well under Chinchilla-optimal). That ceiling caps how good a proposer
Meta-Uchi's autonomous loop has to work with — bigger, more capable reasoning
requires more capacity, not just better orchestration around a small model.

**Intent:** Increase FLUX's parameter count and training token budget for
0.4.0 (exact target TBD against available compute/GPU budget). Carry forward
the two structural wins identified as the biggest levers coming out of v0.3.0:
cut the vocab (currently a 100K-token embedding table eats the majority of
model params — reclaiming that capacity for reasoning layers) and fuse the SSM
scan (removes the throughput ceiling that currently caps tokens-per-hour of
training, so a bigger model can actually see enough data). A bigger, better
FLUX is what Meta-Uchi's tool-calling/reasoning loop is actually delegating to.
This is a compute-bound background job — kick it off now and let it run
alongside Items 1–13; only the exit-criteria validation at the end needs it
finished.

**Progress as of this writing:** Phase 1 (pretrain) complete — 64.0M params,
pruned 32,018-token vocab, val loss 5.82 → 4.11 over 5,000 steps. Phase 2 (SFT)
running live: 50,000 examples across SQuAD/Dolly/CodeAlpaca/UltraChat-200k
(fair-budgeted, 12,500 each), 742 steps.

**Pulled forward from 0.5.0's coding-mastery notes: CommitPackFT into Phase 3.**
Phase 3 (CoT distillation) hasn't started yet, so there was a real window to
add repo-level code-change reasoning data before training begins rather than
waiting for a separate release. `cot_distill.py`'s `load_cot_examples` now
fair-budgets across 4 sources (GSM8K, OpenOrca, Magicoder, CommitPackFT)
instead of 3. CommitPackFT pairs a real diff (old/new file contents from its
Python slice) with a real, human-written commit message — teaches reading an
*existing* change and explaining it, which neither CodeAlpaca nor Magicoder
does (both are from-scratch generation only). The `<|think|>` content is a
real, computed fact about the diff (lines added/removed), not a fabricated
reasoning narrative, since the dataset has no separate reasoning-steps field.
Verified against real, live streamed data (not just mocks) before being
folded in. Note: each row is a single file's before/after, not a true
multi-file commit — a useful proxy for understanding code changes, not
literally cross-repository reasoning; that remains a 0.5.0/later concern if
still wanted. The self-generated execution-trace-to-fix data (0.5.0's other
coding item) was *not* pulled forward — it needs new mutation+execution
infrastructure that doesn't exist yet and depends on 0.5.0's own curated
pretraining corpus as its source of correct code to mutate, unlike
CommitPackFT which is a standalone, already-existing dataset.

**✅ Fixed — inference-time pruned-vocab support was missing.** The training
scripts were fixed to load the pruned tokenizer this session, but
`build_generate_fn` (`uchi/flux/inference_engine.py`) — what `Core()` actually
uses to load a live proposer — still unconditionally used the full ~100K
tokenizer. Finishing all four phases would **not** have been enough on its own:
the moment the new checkpoint was promoted to the default checkpoint path,
`Core()` would have fed it out-of-range token IDs against its smaller
embedding table. Now auto-detects the mismatch from the checkpoint's own
inferred `vocab_size` and loads the matching pruned tokenizer automatically,
with an explicit override available for anything other than the default
pruned-vocab file. Verified against the real, completed Phase 1 checkpoint
(loads and generates correctly) and against the current production
`flux_best.pt` (full vocab, unchanged).

**⏳ Still needed once all four phases finish — promotion is a manual step.**
`Core.__init__` only searches the default `uchi/flux/checkpoints/` directory
for `flux_best.pt`/`qat_best.pt`/`cot_best.pt`/`sft_best.pt`. This retraining's
checkpoints are deliberately isolated in `v040_phase1/`, `v040_phase2/` (and
future `v040_phase3/`, `v040_phase4/`) specifically so they can't be
accidentally picked up mid-experiment and silently replace the production
v0.3.0 model. That means finishing training does not automatically make the
new model live — the final artifact needs to be explicitly copied/promoted to
the default path (the same final step `train_all.sh` does automatically when
run as one script) once Phase 4 completes and the new model is confirmed to
actually be better, not just different.

## 1. Meta-Uchi Default Facade (stub)
**Problem:** If every other item builds against internal scaffolding (`GenerateAndGround`, `swarm.py`, `intent_router.py` called directly), it all has to be re-plumbed later when the public API changes. Doing the facade swap last (as originally planned) guarantees rework.
**Intent:** Refactor the public API now, early, before the interesting logic exists: `from uchi import Uchi` instantiates a new `MetaUchi` class; the existing single-instance engine moves to `uchi.Core` for users who want raw trie access. At this stage `MetaUchi` can be a thin wrapper that routes every call straight to a single `Core` instance — no real tool calling, no real delegation yet. Every later item (2–13) attaches its capability to this stable facade instead of to internal classes. Also fix the dead `u.router` docstring reference at `uchi/simple.py:93` while touching this file — replace it with the real name (`pipeline` / `GenerateAndGround`).

## 2. Filesystem Path Guard
**Problem:** Giving an autonomous system the ability to write and execute files is dangerous. But `uchi/code_engine.py` already proves the actual risk surface is small: it writes to `tempfile.NamedTemporaryFile` and runs `subprocess.run([sys.executable, ...])` today, safely, without a dedicated sandbox subsystem. Building a full chrooted workspace subsystem is solving a bigger problem than the one that exists.
**Intent:** Add a single path-validation helper (`uchi/workspace.py`, ~30 lines): resolve every file path tool calls touch against a fixed root (`uchi/workspace/`), refuse anything that escapes it via `os.path.realpath` + prefix check, and reuse the existing tempfile/subprocess pattern from `code_engine.py` for execution. This is a guard rail, not a subsystem.

## 3. Python Scratchpad Environment
**Problem:** Uchi natively predicts discrete tokens; it cannot natively calculate continuous regressions, calibrate probabilistic uncertainties, or dynamically test code.
**Intent:** Extend `uchi/code_engine.py`'s `REPLOracle` (currently `ast.parse` + `py_compile` only — verifies syntax but never runs the code) into a full execution path: run the code via the same subprocess pattern already in place, and return `stdout`, `stderr`, and return code as text tokens. Do not write a second, parallel oracle — `uchi/procedural_memory.py` already has its own separate `REPLOracle` class with the same name; consolidate to one canonical implementation while doing this work rather than introducing a third.
**Depends on:** 2

---

## 4. Tool Calling Interface
**Problem:** Uchi currently has slash commands, but no generalized mechanism to autonomously decide to take an action, execute it, and ingest the result. This is the real gating item — Items 5, 6, 7, 9, 10, 11, 12, 13 all sit downstream of it.
**Intent:** Implement a formalized tool-calling grammar in the trie. Uchi needs to be able to output a specific token sequence (e.g., `<|tool_call|> write_file(path, content) <|end_tool|>`) that halts generation, triggers a local Python function execution, and appends the result to the context before resuming. Initial tools must include filesystem operations and access to the Python Scratchpad. Ship this with logging from day one (see Item 9 below on observability) instead of retrofitting traces later.
**Depends on:** 3

---

## 5. Goal State Compression & Memory Compaction
**Problem:** Tool calling, web browsing, and code execution generate massive amounts of token noise (raw HTML, long stack traces, large tool outputs). Uchi's trie architecture will lose long-context coherence and goal focus if the active context window fills up with raw execution logs.
**Intent:** Introduce a "Memory Compaction" mechanism in `GenerateAndGround` (the actual pipeline object — see revision note above) and the `MetaUchi` state tracker. Before the context window exceeds a designated token threshold, trigger a deterministic summarization pass: read recent tool outputs, update a persistent `GoalState` object with what was learned or accomplished, and drop the raw tool logs from active memory. **North Star constraint:** the summarization pass must itself be oracle-gated — it may only write claims into `GoalState` that trace back to an actual tool output, never a free-form paraphrase. An ungrounded summarizer is a confabulation backdoor into the trie.
**Depends on:** 4

---

## 6. Self-Healing Loop Prevention
**Problem:** The most common failure mode for autonomous agents writing code is getting stuck in an infinite loop: write bad code -> get error -> write the exact same bad code -> get error.
**Intent:** Implement a strict "Negative Pathway Penalty" in the MCTS inner monologue. If a tool call (like the Scratchpad) returns an error, the trie explicitly penalizes the exact sequence of tokens that generated that call. This forces the search engine to explore a structurally different path on the next attempt, mathematically guaranteeing it won't loop on the same failure.
**Known gap (not yet closed):** the loop guard currently only watches tool-call
signatures (`ToolRegistry.dispatch` and `CodeEngine`'s MCTS candidates) — it is
not wired into `swarm.py`'s delegation/decomposition retry path. If a
sub-question spawned by the swarm's map-reduce decomposition fails repeatedly,
nothing currently blocks or escalates that repeat the way an identical failing
tool call is blocked. "Self-healing delegation" is not a real, unified
capability until this is closed: wire the same `LoopGuard` (or an equivalent
fingerprint-based penalty) into `SwarmSynthesizer`'s sub-question retry logic,
and cover it in `tests/test_edge_cases.py`'s dynamic coverage map.
**Depends on:** 4

## 7. Concurrent / Async Tool Execution
**Problem:** If Meta-Uchi needs to read 5 webpages or run 3 independent Python scripts, executing them sequentially creates an enormous bottleneck that destroys the Operations Per Second metric. Note: `uchi/swarm.py` already demonstrates the concurrency primitive (`ThreadPoolExecutor`) for parallel sub-question solving — this item is the same pattern applied at the tool-call level.
**Intent:** Introduce a `<|tool_call_async|>` grammar element. This allows Meta-Uchi to fire off multiple external tool requests simultaneously without halting its internal monologue. It continues reasoning and ingests the results asynchronously as they stream back into the context.
**Depends on:** 4

---

## 8. Dynamic Tool Registration (Zero-Shot Tool Learning)
**Problem:** Hardcoding tools limits what Uchi can do. Integrating proprietary databases or external APIs currently requires modifying Uchi's source code. Note: `uchi/skill_registry.py` already has a working register/discover/dispatch pattern (markdown-frontmatter driven) — reuse its structure rather than inventing a second registry mechanism.
**Intent:** Allow Meta-Uchi to ingest Python docstrings and function signatures natively as "knowledge." A user can pass a Python file to `u.learn_tools("database_client.py")`, and Meta-Uchi will parse the functions, add them to its active tool registry (extending `SkillRegistry`, not replacing it), and understand how to call them dynamically without hardcoded integrations.
**Depends on:** 4

---

## 9. Intelligence Quotient (IQ) Task Router
**Problem:** Not all tasks require the full reasoning capacity of the entire Uchi network. `uchi/swarm.py`'s `SwarmSynthesizer.answer()` already decomposes and aggregates, but it does so unconditionally — it always calls `_decompose()` (a FLUX proposer round-trip) before checking whether the question was even complex enough to need it.
**Intent:** This is a cheap heuristic pre-check, not new infrastructure. Reuse the pattern already proven in `uchi/intent_router.py` (regex/length/keyword classification) to gate `SwarmSynthesizer._decompose()`: low-score tasks skip straight to a single `Core` pass; only high-score tasks pay for decomposition and parallel dispatch. No new communication protocol between nodes is needed — `swarm.py`'s in-process `ThreadPoolExecutor` dispatch already works and has no demonstrated latency problem to justify one.
**Depends on:** 4

---

## 10. Human-in-the-Loop (HitL) Yielding
**Problem:** Autonomous agents inevitably get stuck or encounter high-risk actions. If they brute-force their way through ambiguity, they break things.
**Intent:** Introduce a `<|yield_to_user|>` tool call. If the IQ Task Router detects extreme uncertainty, or if a tool fails repeatedly, Meta-Uchi pauses its token stream, asks the user for clarification (e.g., "I cannot find the login button, should I proceed?"), and seamlessly ingests the human's response to continue the task.
**Depends on:** 4, 9

---

## 11. Web Navigation Toolkit
**Problem:** To have human-like capabilities, Uchi needs to navigate the web. Feeding raw HTML into the trie will destroy the token space and cause massive hallucination. Note: `uchi/web_search.py` already retrieves structured, parsed content (DuckDuckGo, Wikipedia, arXiv, News RSS) with zero browser dependency — this already covers most "look something up" goals.
**Intent:** Scope this down from the original "headless Chromium + full accessibility tree" plan. First, expose `MultiSourceSearch` as a tool call through Item 4 — this alone closes most of the gap. Only add real browser automation (Playwright/Chromium, DOM parsed into abstracted UI tokens like `[LINK: "Log In"]`) as a follow-up if a concrete goal requires interactive navigation (clicking, form-filling) that static retrieval can't satisfy. Don't pay for a browser dependency until a real task needs one.
**Depends on:** 4, 5

---

## 12. Agentic State Checkpointing (Pause and Resume)
**Problem:** If Meta-Uchi is 100 steps into a complex task and the process stops, all active reasoning, `GoalState` tracking, and task progress are lost.
**Intent:** Because Uchi is deterministic, the active `MetaUchi` state can be fully serialized. Implement checkpointing to save the `GoalState`, tool logs, and active token streams to disk. This allows a user to hit `Ctrl+C` to pause the agent, and run `u.resume("task_state.uchi")` later to pick up exactly where it left off.
**Depends on:** 4, 5

---

## 13. Episodic Memory & "Macro" Skill Distillation
**Problem:** When Meta-Uchi successfully solves a difficult, multi-step problem, it stores the solution in transient memory. The next time it faces the same goal, it wastes operations reasoning through the exact same steps from scratch. Note: `uchi/episodic_memory.py` already exists as a starting point — check its current scope before building a second episodic store.
**Intent:** Implement a background "Distillation" pass upon task success. Meta-Uchi extracts the successful sequence of tool calls, removes errors and dead-ends, and compiles it into a reusable "Macro". This sequence is permanently ingested into the core trie, so the next time it encounters a similar goal, it deterministically recalls the fast-path macro instead of reasoning step-by-step.
**Depends on:** 4, 5

---

## 14. Agentic Observability (The "Glass Brain" UI)
**Problem:** When a single-instance sequence predictor fails, you can debug the prompt. When an autonomous orchestrator fails after delegating to several nodes, making concurrent tool calls, and reading web pages, debugging it without a trace is impossible.
**Intent:** Not a gated deliverable scheduled for the end — build a thin structured logger into Item 4's tool-calling interface from day one (which node, which tool, what arguments, what result, what error), and add the TUI visualizer as a display layer over that log once Items 4, 7, and 9 exist. Building the trace format after the fact means retrofitting instrumentation into five already-built subsystems instead of getting it for free.
**Depends on:** 4 (logging from day one); 7, 9 (full visualizer)

## 15. Uchi Operations Per Second (OPS) Benchmark Harness
**Problem:** MMLU and SWE-bench measure static intelligence, but v0.4.0 is about autonomous agency. There is no existing metric to measure how fast and effectively Uchi can execute an autonomous loop.
**Intent:** Create a new benchmark harness: `benchmarks/ops_benchmark.py`. This measures **Uchi Operations Per Second (OPS)**. A single operation is defined as a complete inner-monologue cycle ending in a successful, syntactically valid tool call. This only needs Item 4 (a real tool call loop) and Item 1's stub facade to exist — it does not need the full IQ router or delegation logic finished first.
**Depends on:** 1, 4

## 17. Verifier Upgrade: Layered Neural + Statistical Veto (Trained From Scratch)
**Problem:** `FactCheckOracle`'s word-overlap check is deliberately simple and
auditable, but it's demonstrably too rigid in two different directions,
both found and confirmed live this session: it can be too *lenient* (a
claim mostly overlapping irrelevant-but-wrong evidence clears the support
threshold — "500 meters" passed as grounded against evidence saying "330
meters" because 4/5 salient words matched; it also cannot distinguish a
claim from its negation), and too *strict* (correct paraphrases can fail
purely on wording, not substance).
**Intent:** Add two additional, strictly *additive* veto layers on top of
the existing deterministic check — neither can ever override a rejection
into an acceptance, preserving the one non-negotiable property (the
verifier cannot itself hallucinate a claim into passing):
- **An entailment classifier, trained from scratch** — `HybridTSSM` with a
  classification head (3-way softmax over entailment/neutral/contradiction)
  in place of the generation head, on a *separate* embedding table from the
  main FLUX checkpoint (a structural guarantee the verifier can't share the
  proposer's failure modes, not just a training-time coincidence). Trained
  on `nyu-mll/glue` (mnli config) + `stanfordnlp/snli` — both verified
  against the live HF Hub before committing, real `premise`/`hypothesis`/
  `label` fields, ~1M+ combined examples. Vetoes on high-confidence
  "contradiction" — generalizes beyond exact number matches to catch
  semantic contradictions with no shared vocabulary at all (e.g. "the CEO
  resigned" vs. evidence saying "the CEO was promoted").
- **The existing `UniversalPredictor`/`AnomalyDetector` (`/anomaly`'s
  trie-based surprise-score mechanism), fit on a numeric-facts corpus
  pulled from the semantic index's own ingested passages** — flags a
  claimed number as statistically implausible even when the retrieved
  evidence doesn't contain a directly competing value, a strict
  generalization of exact-match numeric checking. `/classify` and
  `/forecast` were considered and explicitly not used here — classification
  would duplicate what retrieval's embedding similarity already guarantees
  topically, and forecast only applies to trend-shaped claims, too narrow
  to be a general verification signal.
- **Ordering:** logically a strict AND across all three layers, so final
  verdicts don't depend on evaluation order — but all three layers should
  be *evaluated* regardless of whether an earlier one already failed (not
  short-circuited), at least through a calibration period, specifically so
  disagreements between the deterministic check and the smart layers get
  logged and can validate whether the smart layers are adding real value
  before trusting them in production.
- **Training script**: `train_verifier.sh`, mirroring `train_all.sh`'s
  phase structure — tokenize MNLI+SNLI to a memmap, train the
  classification head, optionally ternary-quantize it the same way as the
  main model. Held-out validation against a small adversarial set (in the
  style of the "330m vs 500m" case) required before any live vetoes are
  trusted, same discipline as every other training addition this session.
**Scheduling constraint:** the GPU is fully committed to the Item 0
retraining (Phases 2–4) as of this writing — this item's code, data
pipeline, and scripts get built and validated now (CPU-only, verified
datasets, same as every other source this session), but the actual
training run is sequenced to launch only after Item 0's phases finish, not
compete with them.
**Depends on:** 0 (for GPU availability, not code readiness)

**✅ Code and data pipeline built, CPU-verified — training not yet run.**
- `uchi/flux/verifier_model.py`: `EntailmentClassifier` (HybridTSSM backbone,
  separate embedding table, 3-way pooled classification head) +
  `EntailmentChecker` (the adapter `oracle.py` actually talks to —
  `is_contradiction(premise, hypothesis) -> bool`; `.load()` mirrors
  `FluxProposer.load()`'s graceful degradation exactly, returning `None`
  rather than raising when no checkpoint exists yet).
- `uchi/flux/verifier_train.py`: MNLI (`nyu-mll/glue`, mnli config) + SNLI
  (`stanfordnlp/snli`) loaders, both verified against the live HF Hub
  before use; SNLI's `label=-1` ("no annotator consensus") rows explicitly
  excluded rather than treated as a bogus fourth class; same independent
  per-source fair-budgeting as every other data source this session.
- `uchi/numeric_plausibility.py`: **the original plan to reuse
  `UniversalPredictor`/`AnomalyDetector` was tested and abandoned** — that
  predictor is built for *sequential* anomaly detection (surprise given
  the immediately preceding context in an ordered series); numeric facts
  pulled from scattered, unrelated passages have no such order, and
  empirically every value scored within 0.05 of every other regardless of
  actual magnitude (55 and 50,000 nearly identical). Replaced with a
  simple, deterministic median+MAD outlier check on the same real
  extracted numeric facts — verified to correctly discriminate in-range
  values from wild outliers where the sequential approach could not.
  `UniversalPredictor`/`AnomalyDetector` remains the right tool for
  genuinely sequential claims (a claimed trend/time-series value); that
  connection wasn't ruled out, just this one.
- `uchi/oracle.py`: both wired in as optional constructor parameters
  (`entailment_checker`, `numeric_checker`), defaulting to `None` — zero
  behavior change confirmed by test (`test_no_layered_checkers_behaves_
  exactly_as_before`). 20 tests in `tests/test_verifier_upgrade.py`,
  including a fake always-vetoes checker (proves the veto fires) and a
  fake always-agrees checker applied to a deterministic *rejection* (proves
  a smart layer agreeing can never resurrect a rejected claim — the core
  safety property, tested directly, not just asserted).
- **OOD gate on the entailment veto** (`OODDetector`, Mahalanobis distance
  over `EntailmentClassifier.encode()`'s pooled latent representation,
  fit during training on a real sample of the training set — nearly free,
  those representations are already computed every step). Gates the
  contradiction verdict, never an independent veto: if an input is far
  from anything the classifier was trained on, its judgment is treated as
  "no opinion" for that call rather than trusted — a confident-but-
  baseless verdict on out-of-distribution input is a well-documented
  neural-classifier failure mode (Lee et al.'s Mahalanobis-based OOD
  detection is the standard technique, not novel/unproven here). Verified
  the underlying math directly against synthetic, well-behaved data before
  trusting it (an untrained model's own latent space has no learned
  structure, so testing through it isn't diagnostic of the detector itself).
- **The flywheel** (`uchi/verifier_flywheel.py`): closes the loop the
  "smarter over time" discussion asked for. Reuses the same
  `EntailmentChecker` (no new model) to detect when a user's next turn
  contradicts Uchi's own prior answer — a cheap, real, unsolicited signal
  that something should have been caught but wasn't. Wired into
  `Core.ask()`, purely observational (never blocks or alters the
  conversation). Confirmed corrections export as real, verified training
  examples in the same premise/hypothesis/label shape `verifier_train.py`
  already expects — folded in as a genuine fourth fair-budgeted source
  (`--flywheel-path`), empty/nonexistent until real conversations have
  happened, growing naturally over time rather than being seeded with
  anything fabricated. `uchi/simple.py` wires this in alongside the
  entailment checker (both inert until a verifier checkpoint exists);
  `fit_numeric_plausibility_checker()` added as an explicit opt-in method
  rather than automatic at `Core()` construction, since fitting scans
  every passage in the index (130K+ in the premade brain) — real,
  measurable cost that shouldn't be paid on every startup uninvited.
- `scripts/train_verifier.sh` written, mirroring `train_all.sh`'s shape.
  **Not launched** — explicitly deferred until the GPU frees up per the
  scheduling constraint above.

## Deferred to v0.5 (cut from v0.4.0 scope)

- **Token Stream Communication Protocol** *(formerly Item 8)* — premised on
  JSON/IPC serialization overhead between `Meta-Uchi` and specialized nodes
  destroying latency. No out-of-process or networked node boundary exists
  anywhere else in this plan to justify it, and `uchi/swarm.py` already proves
  in-process `ThreadPoolExecutor` dispatch works with zero serialization cost.
  Revisit only if a real networked/distributed node requirement emerges.
- **Background Dreaming Daemon (Idle Self-Play)** *(formerly Item 17)* —
  stacks three unvalidated dependencies (Web Toolkit, Scratchpad, Episodic
  Distillation) with no defined reward/success signal beyond "the same
  grounding oracle." Revisit once Items 1–15 are proven in production use,
  not as a v0.4.0 exit requirement.
- **Sentence-Level MCTS Verifier Cascade** *(depends on Item 17)* —
  generalizes Item 17's dynamic-N self-consistency voting into a PUCT
  tree search over complete-sentence nodes: `FluxProposer` as the policy
  prior, `EntailmentChecker` (scoring the *full accumulated path*, never
  an isolated sentence — matches its MNLI/SNLI training distribution,
  where an isolated fragment or a context-free continuation would not)
  as the value function, `OODDetector` as a hard pruning mask on
  out-of-distribution branches. No shared weights or gradients between
  proposer and verifier at any point — an earlier version of this design
  explored a shared continuous latent space and inference-time gradient
  flow between them and was explicitly rejected for reintroducing
  correlated failure modes. Real, unresolved dependencies before this
  can be built, not just designed: Item 17's verifier trained and
  temperature-scale calibrated first (an uncalibrated score directly
  biases which branches PUCT commits search budget to, not just which
  side of a threshold a single verdict falls on), and real GPU latency
  numbers (CPU-benchmarked already — depth 3/branching 3, proposer cost

## Expected Benchmarks / Exit Criteria for v0.4.0

Before v0.4.0 can ship, it must be evaluated against the following criteria:

1. **FLUX Scale-Up Baseline:** the 0.4.0 FLUX model must be measurably larger
   (params) and trained on a materially larger token budget than v0.3.0's,
   with a documented before/after on generation coherence (not just loss).
2. **OPS Baseline:** `ops_benchmark.py` must establish a baseline execution speed for a 10-step autonomous task.
3. **Context Coherence:** `Meta-Uchi` must successfully execute a 25-step task without dropping the original user intent.
4. **Zero-Regression on v0.3.0:** MMLU no-parse rates and SWE-bench code generation rates must not regress from the v0.3.0 final numbers when run through the `Meta-Uchi` facade.
5. **Self-Healing Validation:** A test case designed to fail on the first attempt must prove that Uchi successfully alters its code path and resolves the error without looping.
6. **Web Navigation Baseline:** Establish a baseline score for autonomous web navigation capabilities (static retrieval via `MultiSourceSearch`; browser automation only if Item 11's follow-up scope was triggered).
7. **Verifier Upgrade Validation (Item 17):** the entailment classifier and anomaly-based numeric check must each be measured against a held-out adversarial set (contradiction cases word-overlap misses) before being trusted live, and must show zero cases of overriding a rejection into an acceptance — the additive-only property is a pass/fail gate, not a design aspiration.

## 16. Bonus Objective: Crossing the Ecosystem Moat (Stretch Goal)
**Problem:** Uchi is fundamentally a specialized reasoning and verification engine, but users inevitably compare it to ChatGPT. ChatGPT's advantage is a massive ecosystem "moat": general intelligence breadth, multimodality, a polished UX, low latency, and deep integrations. Trying to fight OpenAI on raw compute or headcount will fail. We must use high-leverage architecture to absorb that business value.
**Intent:** While v0.4.0's primary mandate is strict verification and autonomy, an honest attempt to cross the ecosystem moat will be made using these high-leverage strategies:
- **Adopt MCP for the Tool Ecosystem:** Do not write API integrations from scratch. Make MetaUchi an MCP (Model Context Protocol) Client. This instantly grants out-of-the-box access to thousands of enterprise tools (filesystems, databases, APIs) without maintaining the glue code.
- **Fake Multimodality with "Perceptual Ingestors":** Do not train a multimodal FLUX. Instead, use off-the-shelf open-source vision/audio models (e.g., Florence-2, Whisper) as ingestion pipes to convert images/audio into highly detailed text descriptions. The Semantic Index ingests the text, and FLUX reasons over it natively.
- **Become OpenAI-API Compatible (Instant UX Polish):** Make `uchi serve` exactly mimic the OpenAI `/v1/chat/completions` endpoint. This allows users to plug Uchi directly into world-class, polished open-source frontends (like Open-WebUI) without writing any frontend UI code.
- **Mask Latency with "Observable Monologue":** Strict verification inherently takes time. To eliminate perceived latency, stream Uchi's internal processes to the UI in real-time (e.g., "🔍 Retrieving HR handbook...", "⚙️ Writing Python script..."). When users can watch the system working on their behalf, psychological wait time drops to zero.
- **Weaponize Procedural Memory (Network Effects):** When Uchi caches a verified script as an autonomous tool (Procedural Memory), make it exportable as a `.uchi_skill` file. By allowing the community to easily share their custom verified tools, users will build the "general intelligence breadth" for you.
- **"Lazy" World Knowledge (Default Web Fallback):** FLUX at 116M parameters cannot memorize the internet. Make web browsing a transparent default fallback. If the Semantic Index lacks the answer, silently query DuckDuckGo/Wikipedia, dump the results into the context, and verify against that.
- **Infinite Session Memory (The "User Manual"):** Maintain a hidden `user_profile.md` file. When the user expresses a preference ("I prefer Python 3.10"), the Swarm writes it to this file. By auto-ingesting this file at the start of every session, Uchi gains infinite cross-session memory without needing a complex vector database.
- **Enterprise Data Silos (Zero-Trust Guardrails):** Capitalize on Uchi's localized architecture to build strict "Data Silos." Configure Uchi so it can ingest `./finance` but physically lacks OS-level read permissions for `./hr`. This solves the massive enterprise compliance moat that SaaS LLMs struggle with.
- **The "Front-Desk" Translation Pass:** To bridge the gap between strict logic and warm conversation, add a final formatting pass. Feed the verified, dry fact back through FLUX with a system prompt: "Deliver this verified fact in a friendly tone. Do NOT add new facts." Uchi sounds conversational without hallucinating.
- **Retain Chat History (Context Rolling):** ✅ Done. `EpisodicMemory`
  (`uchi/episodic_memory.py`) rolls the last N turns into every `ask()` call
  for the SDK/TUI case. Found and fixed two real gaps in the REST surface
  after this was believed complete: (1) `/v1/chat/completions` accepted a
  full OpenAI-shaped `messages` array but silently discarded everything
  except the last message (`question = user_messages[-1].content`) —
  fixed by threading the full prior history through as conversation
  context. (2) The REST server's `_router` is one global `Core` instance
  shared by every caller (`lifespan()` constructs it once) — using
  `self.episodic_memory` for that per-request context would have mixed
  different clients' conversations together. Fixed via a new
  `Core.ask(..., conversation_context: str | None = None)` parameter:
  when supplied, it overrides `self.episodic_memory` for that call only
  and neither reads from nor writes to it, so REST callers get correct
  per-request history with zero cross-contamination, while the SDK/TUI's
  own single-instance session behavior is completely unchanged. Covered
  by `tests/test_openai_compat.py`.
- **No-Evidence Grounding Relaxation (found and fixed this session):**
  ✅ Done. `FactCheckOracle.is_grounded()` was rejecting every claim when
  no relevant evidence existed, including purely conversational replies
  that never asserted anything checkable — verified live: `ask("Hello!")`
  returned the abstention message, not a greeting. Root-caused to two
  layers: the oracle's own word-overlap check (rejects everything with no
  evidence to check against) and two upstream honesty gates in
  `generate_and_ground.py` (nonsense/OOV check, retrieval-similarity
  check) that abstain before the oracle is ever consulted. Fixed at both
  layers, gated on whether the claim/question asserts anything *specific*
  (proper nouns, numbers) rather than a brittle keyword list of
  greetings — a real factual question with weak evidence still abstains
  exactly as before. Verified this doesn't just relax the oracle when it
  shouldn't: the model currently loaded (`flux_best.pt`, the small
  pre-0.4.0 v0.3.0 checkpoint) generated a fabricated number
  ("The answer is 2.") for "Hello!", and the fix correctly still rejects
  that — a hallucinated specific claim, not a generic reply. This is a
  verification-layer fix only; it does not by itself make Uchi generate
  better conversational replies, that's what conversational SFT data
  (below) is for. Covered by `tests/test_oracle_no_evidence_relaxation.py`.
- **Conversational SFT Data:** ✅ In progress. `UltraChat-200k` is wired
  into `sft_train.py` and is the data source actually training in the
  live 0.4.0 Phase 2 run as of this writing — see Item 0. Directly
  addresses the gap the relaxation above exposed: the currently-loaded
  pre-0.4.0 model has no idea how to answer a greeting and defaults to a
  numeric-QA pattern regardless of context; this is what should fix that
  at the generation level once Phase 2 completes and its checkpoint is
  promoted.
- **"Thought vs. Speech" Separation:** Update the TUI and API responses so Uchi's raw reasoning (code written, facts pulled) is isolated in a collapsible "Thought" block, showing only the friendly "Speech" translation by default.
- **Token Streaming (Zero Perceived Latency):** Implement Server-Sent Events (SSE) in the REST API and async generators in the SDK. By streaming the Front-Desk translation to the UI token-by-token as it generates, Uchi feels completely instantaneous.
- **The Pile for Phase 1 Baseline:** Use massive datasets like The Pile strictly in Phase 1 (Pre-training) to scale FLUX's foundational understanding of English/Code, keeping it strictly separate from Phase 2 instruction tuning.
- **Semantic Fact Injection (Zero-Hallucination Trivia):** Datasets like General-Knowledge, TabMCQ, and Open Trivia Database must NOT be baked into neural weights during SFT. They must be ingested directly into the `brain.uchi` index so facts are retrieved dynamically and accurately.
- **Benchmark Hygiene (MMLU, SWE-bench, ARC):** These datasets must remain strictly quarantined as test scorecards. Do not train on them (Data Contamination). If reasoning improvement is needed, use datasets like OpenOrca in Phase 3 (CoT) instead.
- **OS-Level Execution Sandboxing (Prompt Injection Defense):** Replace the naive Python `subprocess` executor with a true sandbox (e.g., Docker container or WebAssembly/Pyodide). This guarantees that malicious web code ingested autonomously by the agent cannot compromise the host machine.
- **Deep Vector Embeddings (Enterprise RAG):** Upgrade the Semantic Index from basic Skip-gram word vectors to modern deep embedding models (like `nomic-embed-text` or `sentence-transformers`). This allows Uchi to ingest massive 1,000-page enterprise documents and retrieve context based on deep semantic meaning rather than just keyword overlap.
- **Enterprise Observability (OpenTelemetry):** Extend the Glass Brain trace logs with an OpenTelemetry exporter. This allows enterprise teams to pipe Uchi's verification loops, token usage, and latency metrics directly into Datadog, Grafana, or LangSmith, upgrading Uchi from a local tool to a production-ready microservice.
- **Code-Specific CoT Distillation (World-Class Coding):** Expand Phase 3 of `train_all.sh` to include advanced synthetic code-reasoning datasets (e.g., Magicoder's OSS-Instruct). This forces FLUX to learn software architecture and step-by-step planning *before* it generates code, bridging the gap between basic instruction-following and elite software engineering.
- **IDE-Level Scratchpad Tools (LSP & Linting):** Upgrade the Python Scratchpad (Item 3) to include real-time static analysis. By integrating linters (`flake8`, `mypy`) or an LSP, Uchi gets instant "red squiggly line" feedback on syntax and type errors before execution, drastically speeding up the autonomous debugging loop.

This is a non-blocking stretch goal, but a strategic North Star for Uchi's long-term competitive viability.
