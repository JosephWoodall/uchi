# Uchi v0.3.0 — Itemized Deliverables

The five non-negotiables for the FLUX (Proposer) + Uchi (Verifier) release. Each
is stated as the problem it exists to solve and the intent that satisfies it.

---

## 1. Compounding Effect

**Problem:** Knowledge that lives only inside a single running process dies with
it. If every `Uchi` instance starts cold and cannot absorb what another instance
produced, there is no accumulation — the system relearns the same things forever
and never gets smarter across sessions, machines, or users.

**Intent:** Knowledge is persistently stored and compounds across instances via
the Python SDK. `learn(str)` feeds the semantic index; `ask()` returns a plain
string; the output of one instance's `ask()` is a valid `learn()` input for the
next. Persisted brains (`save`/`ingest`) carry that accumulated knowledge forward
so each instance builds on the last with no glue code.

---

## 2. Simplified Public API

**Problem:** A capable engine is useless if every interface exposes a different,
leaky surface. Divergent APIs across scripting, terminal, and service usage force
users to relearn the system three times and make the "identical commands"
promise a lie.

**Intent:** One interface, three transports. The exact same commands work
whether accessed via the **Python SDK** (`Uchi().ask(...)`), the **TUI**
(`uchi tui`), or the **REST API** (`uchi serve` → `POST /ask`). Slash-commands
(`/classify`, `/forecast`, …) dispatch identically everywhere, and the REST
contract mirrors the SDK (`ask` → `answer`).

---

## 3. General Reasoning & Reasoning Chains

**Problem:** A pure retrieval system can only return what it already stored
verbatim; it cannot compose a multi-step answer. But an unconstrained generator
invents plausible-sounding chains that are wrong. Either failure mode makes the
system untrustworthy on anything requiring actual reasoning.

**Intent:** FLUX proposes complex, human-readable chains of thought; Uchi
verifies every link. Each step is checked (grounded against the brain, or
executed/REPL-verified for code/math), and the moment a step cannot be verified
the system abstains and names the failing step rather than guessing. Capability
comes from the proposer; trust comes from the verifier.

---

## 4. Human-Readable I/O

**Problem:** Opaque tensors, token ids, or internal state as the interface make
the system uninspectable and un-composable — you cannot audit what it did, and
one component's output cannot be another's input.

**Intent:** All input and output is clear, transparent, interpretable text.
`ask()` always returns a human-readable string and `learn()` always accepts one.
This is what makes both auditability and the compounding effect (Item 1)
possible: every answer is legible, and every answer is re-learnable.

---

## 5. OOD Generalization

**Problem:** Real questions are out-of-distribution — they are not verbatim in
the brain. A system that can only exact-match collapses to random (or silence) on
anything it has not seen stated before.

**Intent:** FLUX supplies the generative capability to attempt out-of-distribution
questions — proposing candidate answers and reasoning that go beyond stored text —
while Uchi's grounding gate keeps those attempts honest, emitting them only when
they can be traced to brain content and abstaining otherwise. The proposer is
deliberately swappable, so a stronger model raises the OOD ceiling without
weakening the trust guarantee.
