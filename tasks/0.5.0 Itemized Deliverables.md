Uchi v0.5.0 — Itemized Deliverables

Theme: Score at least 85% on SWE-bench — and as high above that floor as the mechanism stack allows — without degrading any of Uchi's existing verified capabilities (ODUSP recall, the verification cascade's precision, retrieval-grounded QA accuracy). Curation (Items 1–4) is necessary but not sufficient on its own; verifying correctness, iterating against real feedback, and planning through novel failures are separate mechanisms, built explicitly as Items 5–8. All of Items 5–8 are ports of prior art already implemented in `efficient_llm_training/` (verified present: `rag.py`, `rl_env.py`, `grpo.py`, `world_model.py`, `mcts.py`, `parallel_thought.py`, `react_agent.py`, `agentic_harness.py`, `tools.py`) — this is integration work, not invention, plus one committed research bet (Item 8, built unconditionally rather than gated on early self-play results).

Honest calibration, stated once and not revisited: 85% exceeds current publicly reported SWE-bench Verified performance from frontier, orders-of-magnitude-larger LLM-based agentic systems. Pursuing it with a from-scratch, no-LLM, ~64M-parameter model is a genuine stretch target, not a conservative estimate — treat it as the ceiling the mechanism stack is aimed at, and report the real number in Item 9 regardless of where it lands, same discipline as every prior release.

**Non-regression contract, threaded through every item below:** any architectural change is acceptable in service of the SWE-bench target as long as it does not degrade Uchi's existing verified abilities. This is enforced with explicit checkpoints, not a one-time check at the end — see Items 2, 6, and 8 below, and the final validation in Item 9.

Items ordered by real dependency.

---

1. Hyper-Curated Pretraining Corpus + Decontamination

Extended with a fourth required source — real GitHub issue→diff pairs at scale (issue description *and* diff, not just the diff CommitPackFT already pointed at) — because that's the actual SWE-bench task shape: read an unfamiliar codebase, understand a bug report, produce a correct patch. Document which of the original (a)/(b)/(c) sourcing options is used for the general-code portion, same as before — this new source is additive.

**Hard gate, not optional polish:** any repo appearing in SWE-bench's fixed evaluation set (astropy, django, flask, matplotlib, pytest, requests, scikit-learn, sympy, and the rest of the full/verified/lite repo list) is excluded from this source **entirely, at the repo level** — not just instance-level dedup against known task IDs. Training on *different* issues from the same repo still teaches repo-specific idioms that inflate the eventual number without proving generalization. This exclusion runs before any corpus reaches Item 2; it blocks entry into Item 2, it does not run in parallel with it.

Depends on: nothing — foundational, starts immediately.

2. Model Compaction — Trained From Scratch on Item 1's Corpus

This is also where the context-length ceiling gets fixed, since it only matters at the point a model actually trains on it. FLUX's SSM backbone already gives O(1) inference memory regardless of context length (dual-resolution A_fast/A_slow HiPPO design + periodic attention recall layers, confirmed in `uchi/flux/ssm.py`/`model.py`) — what's never been true is training it on a window long enough to make that capacity mean anything. Current default is 256 tokens, chosen for a 12GB VRAM budget, not an architectural limit.

Two required extensions, both because "just extend it" undersells what's actually needed:

- **max_seq_len is picked by measurement, not intuition.** SSM scan memory is solved by existing gradient checkpointing (~9GB → ~256MB, already proven in `efficient_llm_training/src/train.py`). Attention is not — the 3–5 recall layers are still standard O(T²). Before committing to a target length, run a micro-benchmark of attention FLOPs/memory at 512/1024/2048 tokens against the current 256, and pick the largest value where attention cost stays subdominant to the (checkpointed) SSM scan cost.
- **HiPPO fast/slow decay timescales get re-initialized, not reused.** The current 2–10 / 10–34 token horizons were tuned for a 256-token window and do not automatically rescale to a repo-scale context — the A_fast/A_slow initialization must be recomputed proportional to the new max_seq_len before training starts.

**Non-regression checkpoint:** after training, run the existing MMLU/ARC/retrieval-accuracy suite against this model before it becomes the base for Items 6 and 8. Context extension and corpus changes both touch the base model's general capability — confirm nothing degraded before building further mechanisms on top of it.

Depends on: 1 (including its decontamination gate).

3.5 Repo-Scale Code Retrieval

Port `efficient_llm_training/src/rag.py`'s `LocalKnowledgeAnchor` — FAISS + sentence-transformer embeddings + cross-encoder reranking + graph edges for relational memory — building a per-repo index (file/function-level chunks) at the start of each SWE-bench task, with the graph tracking imports/call-graph edges for cross-file navigation ("the bug is in file A, but the real fix is in file B it imports"). This is what lets a (now longer) context-limited model work on a large repo: retrieve the relevant slice instead of needing the whole repo in context.

Clarification, not a change: the per-task repo index is the actual task repo at eval time — it is unrelated to Item 1's training-corpus decontamination and is not subject to that exclusion list.

Depends on: nothing, parallel to 1–2 (same reasoning as Item 3 — retrieval doesn't touch FLUX's weights).

5. Execution Sandbox — Shared Infrastructure

Nothing in Uchi's current pipeline runs code and checks pass/fail. Port and extend `efficient_llm_training/src/rl_env.py`'s `ExecutionSandbox` (currently: strip markdown fencing, run code against a single test assertion in a subprocess with timeout) into something that applies a patch to a sandboxed repo copy and runs its real test suite, returning pass/fail plus partial credit (tests newly passing / newly failing). Shared infrastructure — both Item 6 (training-time self-play) and Item 7 (live inference-time verification) consume it.

Two required extensions:

- **Container-level isolation** (Docker/gVisor-class, not bare subprocess) once running untrusted generated code at self-play volume — real `setup.py`/import-time side effects, repeatedly, per candidate, per group, per step.
- **Test-impact-analysis subsetting** — map changed files/functions to the tests that actually touch them (via coverage or import graph) and run only those, not the full suite per candidate. Without this, per-group evaluation cost multiplies by group size × full-suite runtime and the "cheap per attempt" premise the plan leans on evaporates.

Staged, not blocking: subprocess+timeout+a small held-out test subset is enough to start Item 6 on easy-tier problems immediately. Container hardening lands before self-play scales to full-repo suites, not before Item 6 starts.

Depends on: nothing. Built and tested in parallel with Items 1–4.

---

6. Execution-Verified Code Self-Play (training-time)

GRPO (`efficient_llm_training/src/grpo.py`, DeepSeek-R1's algorithm — advantage = (reward − group_mean) / group_std), using Item 5's sandbox output as reward. Sample multiple candidate patches per curated problem, score each via the sandbox, optimize FLUX toward patches that pass more often — including real fail→read-stack-trace→fix sequences as multi-turn trajectories, not just single-shot attempts. Self-distillation from the model's own execution-verified traces.

Two required additions, both because GRPO on sparse reward with no curriculum produces a degenerate gradient (early on, most/all candidates in a group fail identically, reward is uniform, group_std collapses toward zero, advantage signal disappears):

- **Curriculum.** Bucket the curated corpus by patch size (lines changed) as a free, already-available difficulty proxy, and train easy-to-hard. No new labeling effort required.
- **Trajectories are logged in a shared Thought→Action→Observation schema from the start** — the same schema Item 7 formalizes, defined now as a lightweight shared artifact (not Item 7's full tool-interception harness). This is what gives Item 8 real hypothesis-segment training data later, sourced directly instead of invented separately.

**Non-regression checkpoint (diagnostic, not a kill-switch):** after this pass, run the fast MMLU/ARC/HumanEval subset again against the model, and separately record whether the self-play pass-rate curve on held-out curated problems is actually rising. Item 8 gets built regardless of what this shows — but you'll know going in whether its value head has real learning signal to draw on or is training on a flat curve, and whether the fine-tuning pass itself degraded base capability before compounding it further in Item 8.

Depends on: 2, 5.

7. Live Execution-Gated Verification + Agentic Repair Loop (inference-time)

Two parts:

- Wire Item 5's sandbox into the oracle as a new cascade layer: a candidate patch only reaches the user if it passes the real test suite. Same additive-only contract as every other cascade layer.
- Port the agentic feedback loop: `react_agent.py` (Thought→Action→Observation) and `agentic_harness.py` (tool-call interception mid-generation), with new tools registered in `tools.py`'s existing pattern — `run_tests`, `apply_patch`, `read_file`, `grep_repo`. On failure, the real stack trace/assertion diff gets spliced back in as an observation and FLUX gets another attempt informed by real feedback, not a blind retry.

**Explicit tri-state policy, not silent inheritance of the fact-checking cascade's fallback.** Code execution has three outcomes, not two: pass, fail, and timeout/env-failure/flaky. The word-overlap/entailment/numeric/relational fallback chain has no meaningful opinion about whether code works — falling back to it on a sandbox timeout doesn't mean anything. Timeout/flaky/setup-failure is treated as **abstain**, full stop, not a cascade fallback.

**Explicit retry cap: 3–5 attempts**, stated as a number now, not discovered when a stubborn failure iterates indefinitely against the sandbox.

Efficiency fix while this is being built: Uchi's current dynamic-N implementation (`task_config_cache.py`) calls `propose()` sequentially in a loop. Port `parallel_thought.py`'s vectorized batch generation (N branches in one forward pass) so brute-forcing multiple candidate patches per issue doesn't cost N times the latency.

Depends on: 5 (infrastructure built in parallel with Item 6's training run).

8. Latent-Space Planning for Novel Reasoning — "j-space"

Built unconditionally — a deliberate flywheel investment, not gated on Item 6's self-play curve. Port `world_model.py` (DynamicsHead: predicts next latent hidden state from current state + action embedding; ValueHead: scores a latent state) and `mcts.py` (PUCT-style search, AlphaZero's ucb formula, rolled out purely in latent space — no token decoding at intermediate nodes). Redefine "action" from single-token embedding to hypothesis/reasoning-step level, using **Item 6's Thought-tagged trajectory segments** (the shared schema defined there) as the discrete hypothesis units — pooled embeddings of candidate diagnostic directions ("race condition," "stale cache," "off-by-one"), same mean-pooling approach as `proprioception.py`. Hook ValueHead to Item 5's real execution pass/fail as reward, trained via GRPO same as Item 6, so it learns "how likely is this diagnostic direction to eventually produce a passing patch" from real outcomes, not imitated labels.

Runtime shape: for a hard/unfamiliar issue, generate several candidate hypotheses, use cheap latent-space MCTS rollouts to prune to the most promising few, only then spend the expensive full-generation-plus-real-execution-test budget on those, feeding real outcomes back to keep improving the value head.

**Operational definition of "no precedent," so this is actionable at eval time rather than just an honest disclaimer:** when MCTS search fails to find a promising direction, measure distance from the failing case to the nearest known hypothesis embedding. Close-but-failed means the search budget was too small — tune rollout count. Far-from-anything-known means the hypothesis corpus doesn't cover this failure mode — widen Item 1's corpus or Item 6's curriculum, don't just throw more search compute at it.

**Non-regression checkpoint:** re-run the fast MMLU/ARC/HumanEval subset after this pass too — this is a second sequential fine-tune on top of Item 6's, and catastrophic forgetting compounds across passes if unchecked.

Honest limit, stated once since it matters for this item specifically: this makes better use of whatever exposure the model has; it doesn't invent insight from nothing. A bug with no precedent whatsoever in the hypothesis-training data won't be solved by better search over a space that doesn't contain the right direction — the distance-based check above is how that gets caught rather than silently mistaken for a search-budget problem.

Depends on: 2, 5, 6.
